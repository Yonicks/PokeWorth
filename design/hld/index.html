01Product vision

The user photographs one English Pokémon card. The app reads the card name and collector number, finds the matching print in a card catalog, asks the user to confirm when more than one print fits, then shows the available market price with its source, currency and date.

  1. Open the app and tap Scan Card.
  2. Photograph the card inside the alignment guide.
  3. On-device OCR reads the name and collector number, such as 4/102.
  4. Search the card catalog for matching candidates.
  5. Confirm the correct set and variant when needed.
  6. See the card image, details and available market price.

A price is an estimate, not a guaranteed resale value. It depends on the exact printing, condition, language, grading and whether market data exists.

03Architecture

Everything inside the dashed boundary runs on the phone. The only network dependency is the public TCGdex REST API for card records, images and prices. Photos never leave the device.

Component layers

Screens call TanStack Query hooks, the hooks call services, and only services touch native modules or the network. This keeps OCR and the card provider replaceable without changing screens.

Screens State hooks / external API Services Native modules and storage Build and delivery
App shellCamera, navigation, results, manual search and the collection UI.
On-device OCRExtracts text from the photo without uploading it to a server.
Card matcherNormalizes OCR text and ranks candidates by name, collector number and set.
TCGdex APISupplies card metadata, images and pricing where available.
Local storageKeeps history, owned cards and quantities on the device.

Decision: one mobile app and no custom backend. Add a backend only when it is needed for API-key protection, combining more price sources, shared accounts or stronger AI recognition.

05Card identification logic

  1. Run OCR over the image and collect text lines.
  2. Parse the card name (first plausible line near the top) and the collector number, such as 4/102 or TG12/TG30.
  3. Normalize case, accents, spacing and punctuation.
  4. Query the catalog by name.
  5. Score each candidate on name, number and set agreement.
  6. If the result is ambiguous, show 2–5 candidates for manual selection.
  7. Ask the user to confirm the variant (normal, holo, reverse holo and so on) when the catalog or photo cannot tell them apart.
  8. Show the matching market-price estimate.

Scan sequence as implemented

Scoring as implemented in card-matcher.service.ts

Name similarity (normalized Levenshtein)× 0.60 Collector number exact match+ 0.40 Printed set size equals set's official count+ 0.20

Scores cap at 1.0. When no number is read, the name score is rescaled so it alone can reach 1.0. A match counts as confident only at ≥ 0.85 and at least 0.15 ahead of the runner-up; anything else goes to the Confirm screen.

Rule: never silently treat a low-confidence match as the exact card.

09MVP acceptance criteria

  • OpenUser can photograph a real English Pokémon card on iOS or Android.
  • OpenOCR detects useful text on a representative sample of cards.
  • OpenApp suggests plausible matches and allows corrections.
  • OpenApp distinguishes, or asks for, the correct set and printing before pricing.
  • OpenResult screen shows the price with source, currency and freshness, or says clearly that no price is available.
  • OpenManual lookup works when OCR fails.
  • OpenCore flow works without a custom backend or login.
